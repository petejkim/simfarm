# Native checkpoints, versions 1–17

Version17 adds `runtime.traffic`: sixteen eight-byte records, active count, update delay and last animation tick. It is the sole live owner for both farm origins; v15/v16 generated `newFarm.traffic` moves here unchanged. Original v1–v16 saves migrate an empty source-default table (delay16, lastTick0), preserving current map and RNG rather than replaying eight startup allocations. Weekly spawning then populates traffic normally. V17 validates record/count consistency and active bounds while retaining unused bytes; copies detach from both input and snapshots. Collision audio notices are transient and never replay on restore. See [traffic.md](traffic.md).

This is a native preservation extension, not a recovered DOS save writer. Files use JSON with `format: "simfarm-native"`, `version: 17`, `scenarioId` (0–7 for original scenarios, null for generated farms), `scenario` and `runtime`. The original SSM saver still needs tracing before compatible export can be offered. The decoder limits input to 1,000,000 bytes in the browser (and characters before JSON parsing), validates scalar/array/record boundaries, and rejects unsupported versions or different crop-definition/town-layout bytes.

For original farms, `scenario.source` retains every byte of the original 139,072-byte SSM in hexadecimal, including unknown sections, reserved records and original contradictory counts. It is independent of mutable state. `world` stores 96×96 column-major cells as little-endian terrain/overlay words plus attribute byte. `regions` preserves 12×12×7 interleaved bytes. `records` stores complete tables as hexadecimal; no unknown record member is dropped. Farm/calendar and climate channels are explicit values. Version 2 adds the mutable 47,040-byte `schedule` image, independently of the original template. Version-1 files remain readable: their schedules are recovered from the retained original template because that version did not offer schedule mutation. Missing or malformed schedule images in version 2 are rejected. Current farm ledgers override loader defaults, avoiding SF-014 loss/overwrite on native reload.

The table offsets and strides in `src/formats/scenario-records.ts` come from the existing source-verified SSM **loader** (EXE file `0x4543c` onward), not a newly inferred saver. See `reverse-engineering.md` for individual record/definition evidence and executable hash. The reader decodes native records directly through shared original/native validators, derives live active counts, and validates the separate original source when present. It does not reconstruct an SSM image. The original template remains byte-exact. Native runtime equipment validation allows attached implements and field passes at byte-wrapped borders; ordinary DOS input keeps its original stricter position checks. Rendering/movement already bound map access at those edges.

`runtime` preserves 16 raw 128-byte crop definitions (checked against locally imported assets), all three RNG words, complete forecast/weather globals, days advanced, pause/speed, fractional logical tick accumulator, partial-day tick count, disaster state, shared grass wear counter, animation tick and crop-market prices. Loading constructs a new simulation without invoking startup weather or repricing, consuming RNG, advancing a tick, or altering the saved pause state. Saving is synchronous and does not advance the live farm.

Snapshots/listeners, historical equipment notices, last-command feedback and React selections are transient. Navigation requests and open planner/loan panels are also transient and reset when loading or switching farms. They do not affect future simulation rules. The game state remains owned by GameSimulation. Native checkpoints retain more continuation state than the currently decoded original SSM loader; this is documented behavior, not a claim of exact DOS save semantics.

Validation covers all eight original farms, byte preservation/isolation, fractional time, tick rollover, fifth-year climate rollover, both harvesting methods, all treatments, repeated reloads during edge-field work, and an actual valuable plant–fertilize–harvest–sell cycle. Malformed dimensions, lengths, scalar ranges, references, attachment cycles, prices, versions and asset mismatches are rejected before replacing a live game.

React's Save farm action downloads `.simfarm.json`; Load farm uses a local file picker. A fresh simulation and the matching scenario atlas are fully validated before replacing the current session. The UI checks the retained source template against the installed original scenario and aborts pending asset loads when switching farms. A failed load keeps the current simulation; successful load resets view/selection and transient messages, restores saved run/pause/speed, and does not accumulate time spent offline. Saves are explicit downloads; no autosave is claimed.

Automatic field scheduling is now part of normal time advancement. Saves retain the edited/projected schedule image and restore it without executing an extra weekly order. Integration tests reload across year-end and verify exact continuation with automatic work and original crop-price changes. No new file fields are required. Last scheduled-order feedback is transient like other command feedback. Older native files load with their preserved/recovered plans; resuming them uses the current reconstructed simulation, which now includes weekly work that earlier builds omitted.


Version 3 adds canonical financial accounts, annual ledgers, debt/loan values, town development/construction state and the clearing queue. Version 4 adds the terminal default decision, including its pending/restart/end status; a terminal decision requires a paused checkpoint. Older formats migrate missing values using the documented cold-import policy. Existing ledgers are retained, not reset on restoration.

Version 5 adds `runtime.townLayoutBytes`, exactly 1,920 original layout bytes. Loading verifies them against the installed `TownLayouts` before replacing the game, just like crop definitions. Versions 1–4 adopt the supplied asset once and save it thereafter. Town state and terrain already reside in the checkpoint; weekly development now resumes through the normal clock without an extra paint or RNG draw during load. An active built town-owned district with type nibble 15 is rejected because the original table has only fifteen layouts (SF-049). Layouts supplied to GameSimulation are copied so later caller mutation cannot alter a running game. As with prior calendar additions, old checkpoints resume under the current reconstructed rules, including weekly development absent from earlier builds.


Version 6 adds nullable `runtime.pendingTown`: phase `annual-reset`, the reserved site and `resumeRunning`. Collection, ownership reservation, active-site assignment, weekly orders and monthly retries have already happened. Ledger reset, plan projection, rate/weather changes, January installment, forecast and daily growth have not. The date is normalized to January 1 for checkpoint bounds; `daysAdvanced` increases only when that interrupted day finishes. The pending state requires a paused clock, zero partial/fractional ticks, zero sales accumulator, no terminal default, matching active site and town ownership. Before construction the reserved plot's old regional byte may have any type nibble, including 15; preserve it until a valid choice replaces it. No weekly development runs while that raw byte is pending.

A successful choice clears the continuation and runs only its remaining phases. Failed recreation leaves the reservation and phase intact. Loading does not replay taxes, debit town funds again or draw RNG. All commands except choosing a district are blocked while pending; saving/loading and changing scenarios remain available. A running session resumes after a choice with no accumulated waiting time; an originally paused session stays paused. Versions 1–5 migrate to no pending event, then use the current annual rules on future boundaries. Tax notices/results and last-choice feedback are transient; debt, accounts, counters and the continuation are persistent.


Clearing effects now consume the saved animation tick in the live scheduler. Loading a pending queue does not advance it; running/manual time resumes at its preserved sixteen-tick boundary, including word wrap. Native Pause and modal/terminal decisions freeze this queue with other simulation work. Existing v6 fields suffice. Older checkpoints resume under the current live updater, including source-retained overwritten entries (SF-066).


The current Farm report is derived from canonical ledgers and decoded field flags when GameSimulation publishes a snapshot. It is not stored redundantly in checkpoints and does not overwrite the original retained `reportIncome/reportExpenses/reportNet` caches. Reopening/reloading the native report recomputes its display without changing RNG, accounts or field bytes. Annual history now persists separately as described below; original report rendering and full cache lifecycle remain unfinished.


Version 7 adds `runtime.finances.statistics`: the two original raw asset dwords, four region count bytes, fourteen report words, eight presence bytes, distinct-status byte and two word counters. Every member and exact array length is mandatory; byte/word/dword ranges are validated before replacement. Prior cached values may disagree with current map/fields and are retained. Snapshot copies detach all arrays. Versions 1–6 import the verified dwords from their retained source template and initialize absent history to zero exactly once; no old annual event is replayed. This cannot recover history omitted by older native versions. Original warm-load transfer/lifecycle and posting semantics of the two dwords remain unresolved.

Weekly status aggregation now runs before water/status refresh, so the persisted aggregate can differ from the current Farm report. Annual history shifts after tax, town choice, ledger reset and schedule projection, before loan-rate/weather updates and January payment. A pending version-7 town choice retains its pre-annual history and resumes the update once on valid construction. Loading never computes a replacement aggregate or rating. Automatic music requests and original report-window rendering remain pending.

Version 8 adds `runtime.finances.homestead` with saved tile origin `x/y` and remembered rank. Origins 0–92 leave room for the original 3×3 offset footprint; rank is 0–5 or sentinel 255. Current-version members are mandatory. Versions 1–7 migrate the original SSM coordinates and sentinel once, without repainting or emitting feedback. A warm native restore preserves the current rank and map, including a pending town choice before annual repaint. The original SSM rank transfer is unresolved; no rank is guessed from terrain or cash.

Music/sound requests and the last homestead notice are transient presentation events, not checkpoint owners. GameSimulation emits them after finishing a phase and publishing its snapshot. Loading does not replay them. MIDI enable/track/volume and sound enable are user-interface preferences; no autoplay is inferred from loaded financial state.


Version9 adds full mutable irrigation state, including source table, current wave and pending cells; earlier files import their original source state. Version10 adds `runtime.animalFrame`, retaining both animation timestamps and the21-byte herd cache; earlier versions initialize these once. Version11 adds `runtime.aircraftService.selectedChemical` (221..223); earlier versions initialize221 independently of each plane's retained loaded chemical. These subsystem fields remain required in their version and later versions. See irrigation/livestock/aircraft evidence documents for original layouts and explicit native boundaries.

Version12 adds nullable `runtime.aircraftFlight`. An active flight retains equipment slot, captured viewport columns/rows, camera origin, signed local offsets, heading/altitude, spray state/counter, four resource/frame timestamps, turbulence/spin state, queued controls and the pre-flight pause state. Versions1–11 migrate to null because they could not start flights. Current files must explicitly supply null or a valid active object. Validation bounds viewports8..80, input queue32, source byte/word fields, camera/offset ranges and active altitude1..100; it rejects a flight that overlaps town/default decisions, lacks a coherent active aircraft/reserved airport home, has an overdue frame/resource clock, or contains unknown inputs. The32-input cap and captured whole-cell viewport are native policies, not recovered BIOS/window limits.

GameSimulation owns `start-flight`, `flight-control` and paused `step-flight`. Starting captures the prior pause state, clears fractional pacing and runs the flight. Controls consume one per original two-tick iteration; stepping advances at most two logical ticks and stops immediately if flight ends. Pause freezes timers/inputs; speed retains the existing browser pacing multiplier. Flight advances both source timer words while suspending ordinary farm phases and preserving partial-day progress. Ending restores the pre-flight pause state; if it restores pause, unused wall time and fractions are discarded so a large browser frame cannot advance the farm after landing. If it restores running, remaining ticks return to ordinary work. Source DOS wall-clock equivalence is not claimed.

All other farm commands are suspended during flight; map-pointer updates remain transient. Aircraft state and queued inputs are copied in snapshots/restoration. Last start/end feedback is transient and does not replay on load. Tests compare byte-exact native continuations across fractional frames, input queues, wrap, speed/pause changes, actual chemical application, home return and crash bookkeeping, and reject malformed flight data before replacing the farm. Browser controls now start/steer/spray/end the preserved continuation and provide paused stepping. The actual viewport is captured at takeoff and is not changed by resize/zoom after load; rendering/audio remain independent of canonical checkpoint ownership. Engine playback resumes only through subsequent running flight requests and explicit sound enable state.


## Version 13: active disasters

Version 13 adds canonical `runtime.disasters`: enabled state, flags, shared frame delay, last-start and wind-reference clock words, tornado frame/position/directions/frame and start clocks, and the corresponding swarm state plus retained field slot. It also writes the legacy `runtime.disasterFlags` alias; the decoder rejects disagreement with the canonical flags. Tornado and swarm cannot both be active. Directions, frame indices, booleans, clock words and coordinates are checked before replacing the farm. Swarm bounds allow the source retained field-origin-plus-five position through100; destructive map access still rejects coordinates outside0..95. A removed field record can remain the swarm's source bounds. Unknown legacy flag bits are retained.

Versions1–12 had no moving-effect positions/clocks. Migration initializes source defaults and clears only their old provisional tornado/swarm bits (`flags & ~33`); it preserves other flags, including wind. Loading does not start an event, reprice crops, consume RNG or replay sounds. The source wind-reference word defaults to0 and is persisted even though the recovered update branch never writes it (SF-129).

Active effects resume through the canonical clock, including pause, speed, fractional ticks and tornado updates during flight. Snapshot state is detached; notices, last-command results, audio requests and viewport location are transient. Unit and browser tests exercise exact saves and continued crop/building damage, swarm expiry, invalid runtime boundaries and legacy migration. Native v13 remains an extension, not an original DOS save format.


## Version 14: drought and flood continuation

Version 14 adds `runtime.waterDisasters`: the signed-byte weekly `counter`, boolean `scanning`, scan coordinates `scanX` (0–94) and `scanY` (0–93), and retained unsigned words `rawFF6C`/`rawFF6E`. An active scan cannot have X94. The shared disaster flags remain canonical in `runtime.disasters`; the legacy `disasterFlags` alias must match. Existing `weather.precipitationBonus` owns DS6994 and is not duplicated. Source addresses and initial bytes are in `disasters.md`.

Versions 1–13 receive counter0, inactive scanning, zero coordinates and zero raw words. Migration preserves their existing water flags, weather/bonus, map and RNG rather than starting a new scan, repricing crops or inventing damage on load. Prior moving-disaster migration rules remain unchanged. Older files resume under current reconstructed rules; this is not a claim that omitted old runtime can be recovered. The decoder permits retained scan state after a flood ends because the original stop does not clear it.

Active checkpoints resume destruction, shoreline visual RNG, weekly counter/stop order and moisture recovery without replaying event-start sounds. Tests cover partial scans before and after field/building destruction, pause/speed changes, flight suspension, unknown words, malformed boundaries and all eight farms through 70 days and drainage. Browser tests compare actual downloaded saves with canonical simulation and reject malformed v14 input without replacing the current farm.


Manual seed and chemical purchasing uses the existing v14 inventory/chemical records, definition counts, building contents, terrain and expense ledgers. No additional runtime field is introduced. Purchase results, shop selections and sound requests are transient. Live tests verify all20 products through checkpoints and35-day continuation plus actual stored-seed/treatment consumption; browser downloads match canonical state before/after purchases and reload never repeats an effect.

Road/fence/gate construction uses the existing v14 terrain and financial fields. Mixed road shapes, crossing flags, both gate orientations/open states, clearing charges and annual other expenses survive checkpoints without adding a schema field. UI action selection and last construction feedback are transient. Loading never purchases, consumes RNG or replays placement PCM. Live tests cover35-day paired continuation; browser tests compare exact downloaded saves before/after reload and further commands.


Frost, crop-circle and toxic-warning integration also uses unchanged v14 fields: shared disaster flags/start tick, weather temperature/anomaly, market prices, field loss words and terrain. Manual wind shares the already persisted wind state. Loading retains active flags but performs no start operation or audio request; the next accepted daily/animation update applies original stop rules. Transient notices, selected controls and the last result's affected-field list are not checkpoint state.35-day paired tests cover continued evolution, and browser saves are compared exactly before/after active reload.


## Version 15: generated farms and explicit provenance

V15 adds required `scenario.origin` and sixteen `scenario.cropFiles`. Original origin requires a valid unchanged source image and ID0–7, and crop filenames must match that source. Generated origin requires null source/ID and obtains all simulation records, farm/climate/schedule/irrigation state directly from the native checkpoint. Its in-memory SSM version is null. Generated load never calls an original scenario reader or uses a fallback SCEN0. Legacy1–14 files retain the original path and migrate to explicit original provenance.

`runtime.newFarm` is null for original imports and required for generated origin. It preserves cold-start provenance version1 (climate/water options, explicit initial RNG words and year/weekday), address-named raw setup fields, five terrain RNG words,3072 planner scratch bytes, the market mode/16×30 history words and sixteen8-byte traffic records with count/delay/last-tick. Traffic payloads/counts and all array/scalar boundaries reuse source-backed validators. Current RNG/weather/prices and calendar continue to belong to their existing live runtime owners. History/provenance are never used to replay creation or replace these owners. Ongoing market-history/traffic simulation is still pending; serialization alone does not implement it.

Generated rendering loads the common original tile/palette resources and original CRP files, patches the sixteen saved crop slots and creates its atlas without an SSM request. Matching raw crop definitions and town layout bytes are still required. Original restores continue verifying their immutable source against the imported scenario asset. All asset work must succeed before replacing the active simulation. Downloads identify generated farms as `simfarm-new-farm-…`; failed loads leave the existing farm intact. See `new-farm.md` for factory ordering, source evidence and the browser/unit coverage.


## Version16: canonical weekly market continuation

`runtime.market` is required for both original and generated farms. It stores sixteen thirty-word histories, a byte `mood` and the unresolved byte `rawBC72`. Only historical indices0..28 permit null, explicitly representing samples absent from legacy native saves. Index29 must be0..65535. The validator rejects missing/malformed histories, invalid mode/raw bytes and null heads before replacing the session. Original source bytes, definition bytes, existing trade prices and all other runtime fields retain their previous validation.

The live market is owned once in GameSimulation; `newFarm.marketHistory` and `newFarm.marketMood` are removed from newly written checkpoints. V15 generated files move those values intact into `market`, defaulting formerly unrecorded rawBC72 to source cold0. V1–15 original files use their saved crop trade prices as known heads, null for the29 unknown earlier samples, and source cold mode0/raw0 as a documented native migration default. Neither migration runs startup history generation, replays planting/disasters, reprices trade tables or consumes RNG. This cannot reconstruct omitted event/history state from an older implementation.

Weekly updating shifts histories and synchronizes trade tables after all aging phases and before wind/scheduled planting. Planting/disaster events affect history only; a checkpoint between an event and the next weekly boundary must retain different history and trade prices. Null samples shift out naturally after29 weeks. Restore keeps partial ticks, flags, table prices, history and all RNG words, with no update or audio replay. Old files resume with the current reconstructed market rules; behavior identical to older builds without those rules is not claimed. See market.md for exact source arithmetic and live unit/browser coverage.
